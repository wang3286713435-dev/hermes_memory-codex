# Local PR Proposal: Enterprise Memory Usability Follow-up

## Status

这是一份本地 PR 风格提案。

目的不是立刻改主线，而是让后续主线 Hermes agent 明确知道：

1. 当前企业文件记忆能力已经有基础。
2. 但“会用”和“好用”之间还有明显距离。
3. 后续优化重点不该只是 alias 小修，而应是整体企业文件使用体验。

这份提案不是：

1. production rollout 请求
2. 自动经营决策授权
3. retrieval contract 大改授权
4. memory kernel 主架构重写授权
5. evidence boundary 放松授权

## 1. 当前真实问题

当前用户体验里最核心的问题不是“系统不会检索”，而是：

**Hermes 自己并不像真正知道“企业文件记忆系统”是它的原生能力。**

这会带来一连串实际使用问题：

1. 它不会主动把企业文件管理能力当成自己的默认工作方式。
2. 它不会自然地把“找文件、看文件、围绕文件回答问题”当成同一条工作流。
3. 导入文件麻烦。
4. 绑定文件麻烦。
5. 用户得自己记住很多使用咒语。
6. 员工会觉得“还不如自己去文件夹里找”。

如果这一点不改善，哪怕 retrieval 本身正确，真实公司使用意愿也会很低。

## 2. 当前暴露出的典型症状

### 2.1 Hermes 不像知道自己有企业记忆能力

用户会期待它这样工作：

1. 我提到一个公司文件、一个标书、一个纪要。
2. Hermes 应该优先联想到：
   - 我是不是要找文件
   - 我是不是要看文件内容
   - 我是不是要围绕这份文件继续工作

但当前体验更像：

1. 用户必须先自己记得去绑定 alias。
2. 用户必须自己猜现在有没有 active document。
3. 用户必须自己记得 session 有没有恢复。
4. Hermes 不总是主动告诉用户“我可以帮你找文件并记住它”。

### 2.2 找不到文件时，Hermes 没有很好地承担“文件管理员”的角色

用户真正需要的不是一句“没有找到名为主标书的文件”，而是更接近下面这种帮助：

1. 我没有在当前 session 里锁定这份文件。
2. 我找到了这些候选文件。
3. 它们的标题、路径、版本分别是什么。
4. 你是不是要用其中这一份。

也就是说，用户不是只要一个“失败提示”，而是要一个“主动协助找文件”的 agent。

### 2.3 围绕文件提问时，还不够像“理解我要干什么”

用户希望的是：

1. 我在问一个文件内容时，Hermes 应该知道我要的是“文件里的准确内容”，不是泛泛回答。
2. 我在问“这份文件在哪里”时，Hermes 应该优先返回文件地址、标题、版本、来源。
3. 我在问“继续看刚才那份文件”时，Hermes 应该优先沿用当前文件上下文。

当前体验的问题不是完全做不到，而是这些路径还不够自然和稳定。

### 2.4 导入和绑定的前置动作太重

现在的使用门槛仍然偏高：

1. 要先导入文件。
2. 再考虑怎么绑定 alias。
3. 再考虑 session 作用域。
4. 再考虑 resume。

这对技术人员还能接受，但对普通公司员工很不友好。

## 3. 我们真正想要 Hermes 变成什么

我们要的不是“一个能检索文件的 CLI 工具”，而是：

**一个把企业文件记忆视为自身原生能力的主 agent。**

它应该具备下面几种默认心智。

### 3.1 把企业文件管理当成自己的原生能力

当用户提到：

1. 标书
2. 会议纪要
3. 清单
4. 方案
5. 合同
6. 某个公司内部文件

Hermes 应该优先意识到：

1. 我可以去企业记忆里找这份文件。
2. 我可以帮助用户锁定这份文件。
3. 我可以围绕这份文件持续回答。
4. 如果没锁定，我应该主动提示下一步，而不是只报错。

### 3.2 把“找文件”这件事主动做好

当用户说：

```text
主标书在哪
```

或：

```text
帮我找到兄弟高登这个标书
```

Hermes 理想上应优先返回：

1. 文件标题
2. 文件路径 / 文件地址
3. document_id / version_id
4. 是否是当前推荐使用版本
5. 如果有多个候选，给出最合理的候选列表

而不是只停在“未找到文件名”这一层。

### 3.3 把“围绕文件工作”这件事做成自然工作流

理想流程应该接近：

1. 用户说“帮我找到主标书”
2. Hermes 找到文件并告诉用户路径和标题
3. Hermes 自动或半自动把它设成当前工作文件
4. 用户继续问“建设单位是什么”“最高投标限价是多少”
5. Hermes 保持围绕同一文件回答

也就是说，文件发现、文件锁定、文件问答应该尽量连成一条自然路径。

### 3.4 把“文件内容回答”做得更像专业助手

用户的目标不是看技术 trace，而是高质量完成工作。

所以当用户问文件内容时，Hermes 应该尽量做到：

1. 完整
2. 准确
3. 带 citation
4. 带 document_id / version_id
5. 在需要时带文件路径
6. 没 evidence 时老老实实说 Missing Evidence

### 3.5 把导入和绑定变得更轻

最终理想状态应该是：

1. 导入文件可以更自然语言化。
2. alias 绑定可以更自动。
3. 用户不需要强记固定句式。
4. 用户更像在和“会管理文件的秘书”对话，而不是和“要求严格语法的系统”对话。

## 4. 这份提案对应的明确改动需求

后续主线 Hermes agent 应重点考虑下面几类优化。

### 4.1 Native enterprise memory awareness

主 agent 应更明确知道：

1. 企业文件记忆不是外挂能力，而是核心能力之一。
2. 提到文件时，应优先触发文件发现 / 文件锁定 / 文件问答思路。
3. 回答失败时，应优先提供文件管理层面的帮助。

### 4.2 File discovery first UX

当用户意图是“找文件”时，Hermes 应优先给出：

1. 候选文件标题
2. 路径
3. 版本
4. 推荐下一步操作

而不是只返回简单的 not found。

### 4.3 Lower-friction alias and active-document binding

应降低下面这类说法的使用门槛：

1. `把当前主标书设为 @主标书`
2. `继续看刚才那份文件`
3. `把这份会议纪要记住`

后续方向应包括：

1. 更稳的标题绑定
2. 更稳的当前文件绑定
3. 更清楚的失败诊断
4. 更自然的自动锁定或半自动锁定

### 4.4 Better operator feedback

当绑定失败时，Hermes 应该尽量说清楚：

1. 当前 session 没有 active document
2. 当前不是之前那轮 session
3. 找到了多个候选文件
4. 建议改用哪种更明确的绑定方式

### 4.5 Better file-answer ergonomics

当用户围绕文件提问时，Hermes 应更主动返回：

1. 文件标题
2. 文件路径
3. document_id / version_id
4. citation
5. 当前回答是否只基于这份文件

### 4.6 Natural-language import should become easier

用户未来理想上可以更自然地表达：

1. `把这个文件导入企业记忆，并命名成主标书`
2. `把这个纪要收进知识库，后面我还要继续问`
3. `把这个方案作为 C塔方案记住`

这部分不要求当前立刻实现完整真实上传闭环，但应作为后续明确方向。

## 5. 一个更符合预期的目标体验

理想使用体验应该接近下面这样：

### 场景 A：找文件

用户：

```text
帮我找到兄弟高登这个主标书
```

Hermes：

1. 返回候选文件标题
2. 返回文件路径
3. 返回当前推荐版本
4. 主动问“是否将这份文件设为当前工作文件”

### 场景 B：自动延续文件上下文

用户：

```text
继续看刚才那份主标书，建设单位是什么
```

Hermes：

1. 沿用当前文件
2. 给出建设单位
3. 给出 citation
4. 给出文件标题 / version 信息

### 场景 C：找不到文件时给帮助而不是报错

用户：

```text
把当前主标书设为 @主标书
```

Hermes 理想上不应只说：

```text
没有找到名为主标书的文件
```

而应更接近：

1. 当前 session 里还没有锁定文件。
2. 你可以说 `把《主标书》设为 @主标书`。
3. 或者我可以先帮你查找主标书候选文件。

## 6. 约束与非目标

这份提案不是要求后续顺手扩成：

1. project-level alias 全量重构
2. memory kernel 主架构重写
3. retrieval contract 大改
4. 自动审标 / 自动经营决策
5. evidence boundary 放松

当前仍必须保持：

1. `facts_as_answer=false`
2. `transcript_as_fact=false`
3. citation / evidence 仍是硬边界

## 7. 为什么这个改动重要

这个问题本质上不是“锦上添花”。

它直接决定公司员工会不会愿意用 Hermes。

如果员工主观感受是：

1. 导入太麻烦
2. 绑定太麻烦
3. 还不如自己去文件夹里翻

那即使底层 retrieval 和 citation 做得对，也很难形成真实使用习惯。

所以这个提案真正要推动的是：

**让 Hermes 从“能检索文件的系统”变成“愿意帮人管理和使用企业文件的 agent”。**
